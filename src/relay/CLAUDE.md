# CLAUDE.md: `src/relay/` (the relay, `racecast-feeds.py`)

Loaded when working under `src/relay/`. The root CLAUDE.md keeps a short summary
and the security boundaries; this file holds the relay's mechanisms, gotchas and
design rationale. Read it before changing the relay or any page or endpoint it
serves, even when the file you edit lives elsewhere (`src/obs/`, `src/director/`,
`src/cockpit/`, `src/console/`, `src/racecontrol/`, `src/scripts/`, `tests/`).

## The relay, the heart
A 2-feed "ping-pong": **Feed A** (port 53001) serves odd stints, **Feed B** (53002)
even stints; at each handover the off-air feed advances to the next stint's
commentator stream, so OBS media sources never change URL. A 3rd **POV** feed
(53003) is an optional driver picture-in-picture, paused at start. The schedule is a
Google-Sheet tab read as CSV (no API key); a running feed is never torn off
mid-stint: sheet edits apply on the next `/next` (handover) or `/reload`.
**Qualifying mode** (issue #124): a second `ScheduleSource` reads a separate
`Qualifying` tab (same URL/Streamer/Stint structure); `Relay.mode` ∈
{race, qualifying} and `self.source` is a property returning the active one, so
every path (status/next/reload/set_stint/handover) is mode-aware. Qualifying is a
single stream → it lands on Feed A (B idles). Switch at launch (`--qualifying` /
`racecast event start --qualifying`) or live via `/mode/race`|`/mode/qualifying`
(`set_mode`, re-points feeds like a takeover); the panel has a Qualifying section
(mode toggle + a one-row editor writing the Qualifying tab via the `schedule`
webhook action with `tab:"Qualifying"`). On switch the HUD Streamer/Stint follow
the qualifying row (the issue #112 path).
**Qualifying in the event lifecycle.** Qualifying is also a first-class *broadcast
Part*: a `Q` row in the `Producer` tab (its own Stream Key) is the qualifying
broadcast, and the Director-Panel Parts control is **mode-gated**,
`producer.active_producer_rows(rows, mode)` selects the numeric parts in race mode and
the single `Q` part in qualifying mode (a part is qualifying iff its label, uppercased,
starts with `Q`). Because `Q` is the only (= last) part, ending it fires the existing
last-part auto-stop → report → teardown, so `racecast event start --qualifying` (or the
Control Center **Qualifying** toggle at Start Event, `ui_ops` `_qualifying_flag`) runs a
clean, separate qualifying session with its own OBS stream key. `set_mode` resets the
part pointer to Part 1 on a live mode switch (unless a part is on air). The post-event
**report title** gains a `— Qualifying` marker (`_relay_mode`/`_qualifying_title` in
`racecast.py`, read from the live relay `/status`). The **Director Panel** shows the
schedule editor matching the mode (race editor `#urlsBox` vs the qualifying row
`#qualRow`; the mode toggle, submissions and Parts control stay visible in both). The
cockpit tally/plan, the race-control desk, `/schedule/data` and submission *target*
resolution are already mode-aware (they read the mode-aware `relay.source`); cockpit
stream-link **submissions record their `mode`** so the director's approve writes the
qualifying row via `qualifying_set` (the confirm phrase for the Q part reads
`START PART Q`). Spec/plan:
`docs/superpowers/{specs,plans}/2026-07-05-qualifying-event-lifecycle*.md`.

Pull pipeline per feed: **YouTube**: `yt-dlp -g` resolves the live HLS URL (passing
YouTube's bot-check via `yt-cookies.txt` + deno JS challenge) → `streamlink
--player-external-http` serves that URL to one OBS client. **Twitch**: routed directly
through Streamlink's Twitch plugin (no yt-dlp hop); gated feeds optionally use
`twitch-cookies.txt`. **Local** (#592), a Schedule URL cell `local:` reads the
producer machine's capture card (`RACECAST_CAPTURE`; game audio defaults to the card's own audio device found by name in ffmpeg's device list: `scan_capture_audio`, override/`none` via `RACECAST_CAPTURE_AUDIO`, from the
machine `.env`) with the relay's own `ffmpeg` writing MPEG-TS to stdout at the same fan-out
seam (`local_capture_cmd`, bitrate capped by `LOCAL_VIDEO_KBPS` against the 16 MB ring);
no resolve, cookies or quality tiers, fan-out required. The producer's commentary mic
for that stint is the OBS input `Commentary Mic Device` (#593, in `Stint` + `Splitscreen`,
shipped muted, `RACECAST_MIC`): the relay opens it only while the local feed is on air
and mutes it on every other handover/SPLIT (`obs_ws.feed_audio_plan`, snapshotted in
`Relay.obs_audio_plan`; only on an endurance machine with `RACECAST_CAPTURE`, never in
solo, where the mic ships hot). A STINT press uses the same plan through
`GET /obs/stint/<A|B|live>` / `POST /obs/stint` (`apply_stint_state`; `live` is the
relay's on-air feed, the panel's single STINT macro, #729; A/B is a hand pick: Companion
and the panel's emergency switch), the panel macro calls only that, Companion calls it after its direct OBS actions (the break-glass path when the
relay cannot reach OBS; they never touch the mic), and the smoke test does the same. A failed switch (collection imported before #593) is a relay-log WARNING. Since #670 a machine whose `ffmpeg` can open the mic (`mixes_mic`) mixes it into the local feed instead, and then the OBS input is only ever muted: `_maybe_remute_mixed_mic` (#721) reads it on every OBS probe and mutes it again if anything unmuted it, because a live OBS copy doubles the voice ~3 s early (WARNING + a `mic_remuted` health event, counted in the post-event report; a refused mute is retried every probe but warned once). A local stint that runs without the mixed mic (`Feed.mic_mixed` False: mic missing, unopenable, or on another clock) is the exception (#1124): `obs_audio_plan` gives that feed the OBS input and `_maybe_remute_mixed_mic` opens it on the probe while that feed is on air (`mic_fallback` event), and `mic_fallback_fact` raises a notifiable health yellow. Only a mic ffmpeg could not open drops the mic (`Feed._note_local_failure` reads ffmpeg's `Error opening input file` line); a card the clock probe cannot open is `LOCAL_DEVICE_BUSY` and retried with the mic. Only the director/sheet can set
it (`is_feed_source`); the commentator submit and POV paths stay on `is_channel`. (`curl`-ing a feed port returns nothing, it serves a single
consumer; that is not a failure.)

**Feed fan-out (`RACECAST_FEED_FANOUT`, machine `.env`, DEFAULT ON, live-verified 2026-06-29; set `=0` to fall back).** By default the relay is the single `streamlink --stdout` consumer per feed and re-serves the byte stream via an in-relay `FeedFanoutServer` (`FeedRing` bounded byte ring on the same loopback feed port) to OBS *and* the Director Panel preview simultaneously, eliminating the ~2 s stale-on-activation glitch and making the preview tap free (no second pull). Health moves from "serve process exited" to "bytes stopped flowing": a byte-stall watchdog (`RACECAST_FEED_STALL_S`, default 20 s since #488; `FANOUT_STALL_S = 8.0` survives only as `feed_stalled`'s default parameter) kills the reader and drives the DROP state. Because that makes the watchdog the authority on a dead source, streamlink's own early stop is **derived** from it here (`queue_deadline_factor`, fed to `--stream-segmented-queue-deadline` on both platforms) so it can never fire first: the flag is a multiplier on the playlist's `#EXT-X-TARGETDURATION` (measured 2026-09-21: YouTube 5, Twitch 6), which the broadcaster picks, so a fixed factor silently inverts the order whenever the watchdog moves, which is what #488 did when it raised the watchdog 8 → 20 s. Direct-serve has no watchdog, there streamlink's early stop *is* the detector and keeps `QUEUE_DEADLINE_FACTOR`. The fan-out reader PIPEs streamlink's stderr (its only diagnostic channel here, stdout is the video bytes) and pumps it to `feed_X.log` with a `[streamlink]` tag, parity with direct-serve; discarding it once left every fan-out stall/EOF unexplained. **Caveat. VOD vs live:** because the in-relay ring overflows (the reader never blocks), there is NO consumer backpressure, so against a finite **VOD** streamlink races ahead at multiples of real-time → it reaches EOF in minutes (reconnect churn) and its bursty re-fetch can trip the stall watchdog; a real **live** stream is naturally throttled to ~1× at the live edge, so neither happens. A just-dropped *served* feed is a SILENT health blip until it stays down past `HEALTH_CONNECTING_SETTLE_S` (15 s, below the 30 s red grace), so a reconnect that self-heals within a heartbeat does not fire a DEGRADED Discord `@here` (`drop_connecting_notifiable`, unit-tested); a longer stall still surfaces yellow before red, and red (genuine loss) is immediate. The relay also **measures how far OBS is behind the live edge** (#583): `_serve` records the position OBS has accepted at the start of every read cycle (the read itself jumps the cursor to the trailing mark, so only that position shows a slow consumer), `FeedRing.age_at_offset` turns it into seconds, `consumer_backlog` is the live value on `/status` (Director-Panel header pill `BEHIND LIVE`) and `take_backlog_floor` is the per-heartbeat minimum stored in `health-history.db` v9. A floor more than `RACECAST_FEED_BACKLOG_WARN_S` (5 s, uncalibrated until #584) beyond the prebuffer is a quiet, never-paging yellow and a cockpit note (`program_behind_s`), and since 2026-09-21 the relay **sheds it by itself**: `_backlog_shed_tick` (heartbeat, right after the classification it reads) rebuilds the ON-AIR feed's OBS input so the picture returns to the live edge without a director pressing RESET. It is a second REASON on the freeze detector's control, not a second automation, same `f._obs_reconnect()`, same `RebuildGuard` (three ineffective rebuilds then stand down), same cooldown, because two automations turning one control is a race someone debugs mid-broadcast. `RebuildGuard.pending` is therefore a reason tag, and each reason judges only its own rebuild with its own signal; a rebuild still unjudged when the next one fires counts as ineffective rather than being overwritten. The rebuild registers a splice (`_note_obs_splice`, which takes no clock on purpose) so the A/V detector does not flag the relay's own remedy as unexplained. Off by `RACECAST_FEED_BACKLOG_SHED=0`; `RACECAST_FEED_BACKLOG_SHED_TICKS` (default 1) raises the streak, one tick being enough because the classified floor is already a whole-interval minimum. On-air feed only (an off-air one has no consumer under `close_when_inactive`), POV excluded. This **overrides** #581's *"only a human chooses it"*, which came out of Catalunya's 26 black dropouts; the producer's standing preference is automatic recovery with the manual `/obs/feed-reset` (#587) as the fallback, and `RebuildGuard` plus the measured backlog are what make the override survivable. A backlog that keeps GROWING is NOT fixed here (the shed shears it, the slow host rebuilds it, the guard stands down with a warning), that remains #585, whose trigger is stated in seconds per minute: `racecast obs benchmark` reports exactly that as each tier's `backlog_growth_s_per_min`, with `_source_ahead`'s share subtracted so a source still catching up to the live edge does not read as a slow host. See `docs/superpowers/specs/2026-09-21-automatic-backlog-shed-design.md`. `/status` also carries each feed's `inbound_max_gap_s`, the heartbeat's last #535 reading. It is published read-only, so a 2 s poll never steals `take_max_inbound_gap`'s reset. Its gate is serving + fan-out, which is NOT `backlog_s`'s gate: `backlog_s` also needs an attached consumer, while the gap is measured on the source side and stays valid while OBS is away for a rebuild (blanking it there fed the benchmark a leading run of `None`, which let the pre-restart reading through). The heartbeat keeps two maps for this: `_interval_max_gaps` raw for health-history.db, and `_served_max_gaps` with `None` for an interval nothing measured, so a feed going on air between two ticks cannot republish the idle `0.0` as a healthy-looking measurement. `racecast obs benchmark` records it next to the backlog (#619), since the backlog alone shows a bursty source and a slow consumer the same way. Its resolution is the heartbeat's 30 s, and it drops the reading a window inherits from before the restart, anchored on the first actual reading so a leading `None` run cannot smuggle it back in. That rule (`feed_backlog_degraded` + both env parsers) lives in `health_store.py` so the post-event report's backlog-led finding (#586, `report_build._finding`) counts exactly what the director saw; the report reads the configured OBS frame rate from health-store v10 `obs_fps_target`. The relay unconditionally sets `Feed A`/`Feed B` `close_when_inactive` to match the flag. `True` when fan-out is on (OBS drops off-air so no stale backlog forms), `False` when off (restores the safe direct-serve state so a fallback never leaves feeds stuck at `True`); `Feed POV` ships `True` in both modes and is left untouched (best-effort, OBS unreachable → a note, never a crash). Setting `RACECAST_FEED_FANOUT=0` falls back to the proven `--player-external-http` direct-serve path (one streamlink process → one OBS consumer), the coexistence switch stays so a producer can revert instantly; a transport choice, not a league setting. By default OBS and the program-audio monitor are **served only up to a trailing high-water mark `RACECAST_FEED_PREBUFFER_S` seconds behind the live edge** (default 3 s, #533), every read is capped there, not just the join, so a greedy consumer cannot outrun it, holding an in-ring reserve that absorbs bursty-source gaps (`=0` restores the live-edge serve); the Director-Panel preview still taps the live edge. **A restart rejoins OBS** (#614): since the relay owns the socket, a restart would otherwise splice the new stream into OBS's stale demuxer, so `should_obs_reconnect` rebuilds the feed input after a drop **and** whenever a consumer is still attached to the ring, the director's `/reload`, a tier change, and `set_index` on an on-air feed (every `/next` in solo/qualifying). The ping-pong handover is excluded: `close_when_inactive` already dropped the off-air feed. The rejoin **waits out the HLS prefetch burst** first, because the trailing mark is keyed on byte ARRIVAL: a burst that lands inside the prebuffer window sits entirely above the mark, so an immediate rejoin would put OBS at the burst's START, 10-19 s behind live. How long the burst takes to ARRIVE is a download duration (downlink, source bitrate, CDN), so the relay **measures it per serve** instead of predicting it: the rejoin thread watches `last_byte_ts` and takes the first inbound idle of `BURST_IDLE_S` as the burst's end, then waits the prebuffer, then rebuilds. Only two constants are fixed, and both describe the SOURCE's segment cadence, not the connection: `BURST_IDLE_S` (1.0 s: measured 2026-09-20 on YouTube and Twitch, the usable window is ~(0.78, 1.4) because gaps *inside* a burst reach 0.78 s on YouTube while Twitch low-latency's steady cadence is only 1.4-1.9 s) and `SEGMENT_FETCH_BUDGET_S` (1.0 s) as a **ceiling** via `prefetch_land_s(segments, prebuffer_s)`, for a source that never pauses that long. Twitch low-latency does not. A flat 5 s constant was ~3 s short for YouTube ROBUST, which is what started this. Re-measure with `tools/prefetch-burst-probe.py` (no relay, no league needed). A local capture feed (#592) has no `--hls-live-edge` and never waits; a rejoin whose serve was superseded or died during the wait no-ops (`rejoin_is_stale`). `/status` exposes `feed_prebuffer_s` so `racecast obs benchmark` derives the same wait. See `docs/superpowers/specs/2026-06-28-relay-feed-fanout-design.md`.

**Feed covers (`RACECAST_FEED_COVERS`, default ON, #919, live-verified 2026-10-18).** OBS shows black whenever it opens a feed source: every Splitscreen handover (`close_when_inactive` reopens the incoming feed), every input rebuild (RESET, freeze detector, backlog shed, prefetch rejoin). The relay covers that with a still of the same feed. `FeedCoverTap` runs one ffmpeg per fan-out feed that decodes **keyframes only** (`-skip_frame nokey`) and writes `covers/feed-<x>.latest.jpg`; OBS shows a **different** file, `feed-<x>.jpg`, which only `_snapshot_cover` writes, because **OBS reloads an image source by itself whenever its file changes** (a tap writing the shown file made the still flicker every ~2 s). `_refresh_cover` snapshots once when the cover is raised on the program scene and every `COVER_REFRESH_S` only while it is NOT visible on the program, so viewers always see a frozen still. `Relay._ensure_covers` creates the image inputs `Feed A Cover`/`Feed B Cover` through obs-websocket (`obs_ws.ensure_cover_items`: directly above the feed item, with its transform, in `Stint` and `Splitscreen`), so no collection re-import is needed; it retries every 30 s while missing. A 1 s loop (`_cover_loop`) applies the pure `cover_visible`: shown unless **OBS's own play position** proves it plays the feed (`GetMediaInputStatus` mediaCursor advancing for `COVER_PLAY_S`, `media_play_update`), and **never over a hidden feed item** (it would cover the other, on-air feed in Stint). Bytes reaching OBS are NOT that proof: YouTube's 5 s segments reach OBS in bursts and the picture waits for a keyframe, both measured live. `_pre_show_covers` raises the cover at the three cut sites (split, stint pick, `_reflect`) unless OBS already plays that feed, and `Feed.before_obs_reconnect` raises it (forced, only where the feed item is visible) before EVERY input rebuild. **Cover items must never enter `feed_state_intents`/`split_state_intents`**: `reflect_feed_state` aborts the whole handover on a missing item. `/status` `feeds.<X>.cover` = `off`/`missing`/`shown`/`hidden`. Spec: `docs/superpowers/specs/2026-10-17-feed-signal-hold-design.md` Part C.

**Signal hold (`RACECAST_FEED_SIGNAL_HOLD`, default ON, #918, live-verified with an OBS recording 2026-10-18).** A remote on-air feed whose source stalls is covered instead of stuttering: no extra delay and no quality step-down (#619 stands). `_hold_tick` runs in `_cover_loop` before `_cover_tick` and applies the pure `signal_hold_step`. **Engage** only on what viewers would see: OBS stopped advancing a feed it HAD played for 1 s (`media_play_update` `played`/`stalled_since`; opening a source is never a stall) and the source is the cause, either OBS read up to the newest byte (`FeedFanoutServer.consumer_starved`; NOT `consumer_backlog`, the AGE of OBS's position, which grows during a stall) or the source has been silent past its own cadence (`source_silent_s(segment)` from the Part A target duration; 5 s YouTube segments make 2-5 s byte gaps normal). OBS also bridges ~10 s of source silence from its own buffer, which is why "no bytes" alone is no trigger. Engage: the cover is forced up (its still is never swapped), the input is muted only if OBS reported it unmuted (`muted_by_us`), and `/hud/data` shows the Configuration `Signal Hold` text (`apply_signal_hold_notice`, no Sheet write). **While held** the hold owns OBS's rejoin: `Feed.defer_rejoin` skips a serve restart's prefetch rejoin (two rejoins made OBS catch up, then resync). It survives OBS dropping its socket and the 20 s watchdog restart; only a stint change, a stopped feed or RESET (`Relay.obs_feed_reset`) cancel it. **Release** after `release_steady_s(segment)` of steady bytes (`Feed.steady_gap_s`), or `HOLD_MAX_S` (timeout + WARNING): one rebuild at the live edge under the cover, then a **settle** until OBS plays for `HOLD_SETTLE_S` with the cursor at 0.8-1.25x real time AND a changing source thumbnail (`motion_update`; the cursor can run on the audio while the picture stands), bounded by `HOLD_SETTLE_MAX_S`; then cover, mute and notice lift together. The backlog shed and the freeze detector stand down for a held feed. Tick failures log a WARNING once per distinct error (a debug-only log once hid a hold that could never engage). A mute or unmute the director sets through the relay (`/obs/audio` -> `note_director_mute`) during a hold or settle hands the audio to the director; a click directly in OBS bypasses the relay and is not seen. A picture that never changes (slate, paused replay) counts as playing after `MOTION_FALLBACK_S` of real-time play. The cover tick reads each scene once (`obs_ws.get_scene_items`), never a cached visibility. `/status` `signal_hold.phase` is `hold` or `settling`. Local stints never hold. Note for testers: OBS's local audio monitoring can play the catch-up audio of a muted input; the program output and recordings stay silent. Spec: `docs/superpowers/specs/2026-10-17-feed-signal-hold-design.md` Part B.

**Cookie age and refresh (#1091, #1092).** Only YouTube resolves read `yt-cookies.txt`, so `Relay.cookies_needed()` (any YouTube source in the race schedule, qualifying row or POV) gates `cookie_health(..., needed=)`: old cookies nobody uses are never `stale`, and the panel banner, health yellow and startup log stay quiet; the CLI/Control Center read that verdict from `/status` (`preflight.cookies_needed`). With `RACECAST_COOKIES_BROWSER` (machine `.env`, bare browser name from `COOKIE_BROWSERS`) a `CookieRefresher` thread re-exports each EXISTING jar a feed needs once its export is `COOKIE_REFRESH_AGE_H` old (`export_cookies(..., platform)`, the filtered #616 path); a failed export keeps the jar and backs off `COOKIE_REFRESH_RETRY_S` per platform. A yt-dlp resolve running during an export can write its older jar back, the same race a manual mid-event `racecast cookies` has; the next refresh repairs it.

Control is an **unauthenticated** `ThreadingHTTPServer` on port `8088` exposing GET
endpoints (`/next`, `/reload`, `/set/A/<n>`, `/pov/reload`, `/timer/*`, `/status`,
`/panel`, plus the served pages `/hud`, `/splitscreen` and the per-league overlay assets
`/hud/override.css`, `/splitscreen/override.css`, `/overlay/fonts/<file>`, …)
driven by Companion's Generic-HTTP module. `/next?transition=<cut|fade|stinger>&duration=<ms>`
(the panel, #730) cuts with that transition via `obs_ws.select_transition`; a bare
`/next` (Companion) keeps the hard cut. For the panel `/status` adds `handover_next`
(off-air feed, its stint, `link`, `pending` submission; dropped for non-director console
roles) and, in solo, `template`. `POST /obs/stint {"feed":X,"take":true}` (the panel's
emergency switch) also makes X the relay's on-air feed once OBS took the change
(`Relay.take_on_air`: X's row goes on air, the other feed moves to the next slot and
stops under manual arm); Companion's GET form never takes. `/preview/source/<key>`
serves solo tiles from an allowlist (`SOLO_PREVIEW_SOURCES`: capture, webcam, tyres for
commentary only) through `get_source_screenshot`; over the console it is director-only,
unlike the rest of `/preview/*`, because a solo webcam can be off program. `--bind` defaults to **`auto`** (plug &
play): it binds `127.0.0.1` (OBS always reaches the HUD/feeds on the fixed loopback
address: the OBS collection never needs editing) **and** this machine's Tailscale IP
(auto-detected via `detect_tailscale_ip()`, the `100.64.0.0/10` CGNAT range) when
present, so remote directors/tablets reach `/panel` + `/hud` over the tailnet: *without*
exposing the unauthenticated server on the local LAN the way `0.0.0.0` would. If
Tailscale is down, `auto` falls back to localhost-only (OBS keeps working). Pass an
explicit value (`127.0.0.1` for local-only, or `0.0.0.0`) to override. The endpoints
have no auth and `/status` reveals stream URLs, so the tailnet is the trust boundary,
keep it to invited members. Bind logic is pure + unit-tested: `tests/test_bind.py`.

**Keep awake (#1105).** Once the relay owns the control port it holds an idle-sleep block for its own lifetime (`src/scripts/keep_awake.py`, stdlib only): Windows sets `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` on a dedicated thread (the flag belongs to that thread and dies with the process), macOS runs `caffeinate -i -w <relay pid>`, Linux `systemd-inhibit --what=idle:sleep --mode=block` around `tail --pid=<relay pid>` (the `sleep` block also holds back a manual suspend; desktops auto-suspend through logind, so `idle` alone would not stop them). Both helpers end with the relay pid, so a crash or `taskkill /F` leaves no block. A missing or failing helper logs one WARNING and the relay runs on. `/status` `keep_awake` = `{held, method, note}` (crew console roles see only `held`); `RACECAST_KEEP_AWAKE=0` (machine `.env`) turns it off. Tests: `tests/test_keep_awake.py`.

**Logging.** The relay and each static-stream feed write timestamped, leveled lines
(`YYYY-MM-DD HH:MM:SS LEVEL …`) to per-service log files under `runtime/<profile>/logs/`
via `src/scripts/logsetup.py` (`TimedRotatingFileHandler`, daily midnight rotation,
archive suffix `.YYYY-MM-DD`). Old archives are pruned on each service start: the
retention window defaults to 7 days and is overridable with
`RACECAST_LOG_RETENTION_DAYS`. Each relay feed has its own `feed_A/B/POV.log`; the
streamlink child's output is pumped through the feed logger with a `[streamlink]` tag
and classified levels (ERROR for 4xx/fatal, WARNING for retries). The `relay` and
`streams` CLI log sources are **merged-file views** (console + all feed logs in one
stream); `aggregate` is the default Control Center source and merges all live sources
(relay, streams, OBS, Companion, Tailscale). OBS Studio and Companion logs are
read-only from their native app directories; the Tailscale source appends a
timestamped `tailscale status` snapshot on each service start and on
`racecast tailscale status`. Archive history is accessible with
`relay|streams logs --list` / `--archive <date>` (racecast sources) or by filename
token (OBS/Companion).

The same server also hosts the **lower-third HUD** as one relay-served page,
replacing ~13 cropped Google-Sheets-editor browser sources (the old producer-lag
culprit): `/hud` serves `src/obs/hud.html`, `/hud/data` returns the overlay JSON
(`HudSource` reads the **Overlay** tab for live values + the **Configuration** tab's
brand-text column, header `Brand Name`/`Brand Key`/`Brand`, see `BRAND_TEXT_HEADERS`,
for team→manufacturer), and `/hud/assets/{flags,brands}/<name>`
serves bundled logos from `src/assets/`. The page polls `/hud/data` (no manual
reloads); flags/brands resolve from text via `asset_key()`. Flags: `--no-hud`,
`--overlay-tab`, `--config-tab`, `--hud-poll`, `--overlay-dir` (per-league override
CSS/fonts, passed by the CLI when `profiles/<active>/overlay` exists). The optional
**Quali Times** tab (`--quali-times-tab`, default `Quali Times`) adds each car's
qualifying best lap. Its fetch is **off the HUD refresh path entirely**
(`HudSource.refresh_quali`, called once at boot + by its own `quali_poller` thread every
`QUALI_TIMES_POLL_S` = 60 s, the laps are entered once between qualifying and the race),
so no quali-tab state can delay an on-air `refresh()` or a synchronous panel-push confirm;
`refresh()` only reads the last-good map. A fetch/parse failure keeps that **last-good**
map (never rolled back to empty) and warns once, an
existing tab whose header was renamed/removed replaces the map with empty, and a league
that never created the tab simply stays empty. A lap is matched per **car**: the verbatim
`Team` cell first, then the `#NNN`-stripped name, so two cars of one team keep their own
lap while a bare row still matches every car. The Configuration tab's `BG Color`/`Text

**GT7 telemetry heartbeat (solo POV, #324/#711).** `_telemetry_loop` sends the `~` heartbeat, which requests the 344-byte extended packet (steering, motion, driver pedal input on top of the base `A` fields). `gt7_crypto.decrypt_typed` accepts `A`/`B`/`~` by testing each IV XOR against the magic. Non-obvious console behaviour, verified live: GT7 keeps a **running** stream in its format while heartbeats continue, so a `~` heartbeat into a live `A` stream just keeps it `A`. The format only changes after the stream lapses, ~8 s after the last heartbeat. `gt7_telemetry.HeartbeatPolicy` therefore goes silent once on a foreign-format packet, waits until the stream is quiet, then requests `~`. It tries this once per relay start and keeps the base stream if the switch fails. Only one listener can own UDP 33740 on a host: stop the relay before running `tools/gt7-telemetry-probe.py`. Tests: `tests/test_gt7_telemetry.py` (policy), `tests/test_telemetry_endpoints.py` (loop, fake socket), `tests/test_gt7_fixture.py` (real `A` + `~` packets).

**GT7 packet forwarding (solo POV, #1130).** `_telemetry_loop` passes every decryptable packet from the latched console to `gt7_forward.Forwarder` before it records or parses it, so SimHub or GT Race Engineer on the same host still get telemetry while the relay owns UDP 33740. Targets come from `RACECAST_GT7_FORWARD` (`--gt7-forward`): `HOST:PORT` sends the received bytes, `HOST:PORT/A` re-encrypts as format `A` with the packet's own IV. Names resolve once in `Forwarder.__init__` (an unresolvable or duplicate address is skipped with a warning), never per packet. The socket is non-blocking and has `SO_BROADCAST`; a send error never leaves `send`. Windows reports an earlier send's ICMP port unreachable as `ConnectionResetError` on a later `sendto`, maybe to another target (Python's `socket.ioctl` cannot switch `SIO_UDP_CONNRESET` off), so that error is ignored and costs at most that one packet; any other error logs once per target until it works again. In discovery mode nothing is forwarded until the console is latched. `/status` `telemetry.forward` counts per target and is stripped for crew roles on `/console`. A Control Center `.env` edit updates its own environment (`_sync_environ_with_env_file`) and `JobManager` builds the child environment per job, so a relay restarted from the Control Center sees the new value. Invalid entries are logged and skipped at start. The Control Center edits the key (`/api/gt7-forward`, `gt7_forward_write_data`). Tests: `tests/test_gt7_forward.py`, `tests/test_telemetry_endpoints.py`.

**Telemetry recording (solo POV, #785).** `_telemetry_loop` hands every accepted packet to `TelemetryStore.record`, which enqueues it into `gt7_recording.RecordControl`; a writer thread appends it to `runtime/<profile>/telemetry-recordings/<start>.gt7rec.part` and renames the file on stop. The switch is `telemetry-record.json` when present (every `/telemetry/record/start|stop|toggle` writes it), else the profile's `TELEMETRY_RECORD`; a fresh `event start` deletes the file. `relay stop` on Windows calls `taskkill` (graceful first; a console process usually ignores that, so `stop_pid` escalates to forced `/F /T` after a 10 s wait), and the relay's Python shutdown code does not reliably run there: the writer flushes every second and the next relay start renames leftover `.part` files, only after it bound the control port, so a losing second start never touches the live file. The telemetry loop records each packet before it parses it. `racecast telemetry export` (`gt7_export`, which sits above `gt7_recording` and `gt7_context`) replays a recording through `parse_packet` and `TelemetryEngine` (`on_lap`), so `laps.csv` matches the HUD's verdicts. Tests: `tests/test_gt7_recording.py`, `tests/test_telemetry_endpoints.py`.

**Telemetry packet loss (#1107).** The loop counts every datagram in `gt7_packet_stats.PacketStats` (injected into `TelemetryStore`, which stays free of sibling imports): gaps in the packet id at 0x70 are `lost` (this includes undecryptable and unparseable packets, which also have their own counters), late or repeated ids are `reordered`. A backward jump, a jump past `MAX_GAP` or `STREAM_IDLE_S` of silence starts a new stream. `/telemetry/data`, `/status` `telemetry.packets` and the Engineer snapshot carry the counters; `lossy` (5 % over 10 s, held 20 s, while packets arrive) drives the desk's **Lossy network** label and the quiet `telemetry_lossy` health yellow, excluded from the notify level. The recorder writes the counters into its meta records; `gt7_laps` counts id gaps per lap (`packets_lost`, resume point keeps `last_pid`) with the same `STREAM_IDLE_S` restart, minus the recorder queue's own drops from the meta records.

**Wheel slip (#1106).** `parse_packet` decodes `wheel_rps` (0xA4) and `tyre_radius` (0xB4, metres) and derives `slip` per wheel (|rotation| x radius / speed, None below `SLIP_MIN_SPEED_MPS`). `gt7_telemetry.SlipEvents` turns it into lock-up/wheelspin events (`LOCKUP_FLOOR`, `WHEELSPIN_CEILING`, `SLIP_EVENT_MIN_S`); `gt7_laps` stores them per lap (`wheel_events`, `lockups`, `wheelspins`, resume point keeps the open events), `gt7_track_definitions.corner_metrics` counts them per corner, `gt7_channels` offers `slip_fl..rr`. The limits and their derivation from real recordings: wiki Telemetry, "Wheelspin and lock-ups".

**Telemetry context (#811).** `gt7_context` persists optional profile preparation/templates and recording-owned `<stem>.context.json` plus compressed revision history. Recording headers carry a UUID; legacy captures use a header/first-record fingerprint. The relay passes `attach_prepared` as the writer's `on_open` hook, which runs once on a separate daemon thread, so context failure never stops capture; `gt7_recording` itself never imports `gt7_context`. Valid settings and unfinished drafts are separate. Atomic writes plus process-wide advisory locks and optimistic revisions prevent relay/UI lost updates. Context joins the rebuildable lap index at read time, including current report/export snapshots. Confirmed service times split pit-lap membership; inference remains proposed. Contextual roles and known condition/strategy differences filter comparisons without rewriting raw pace quality. Deletion removes only recording-owned metadata; templates remain. Local HTTP mutations require profile/source identity and same-origin validation. Tests: `tests/test_gt7_context.py`, recording/racecast/UI tests.

**GT7 data and track recognition (#787).** `gt7_data` resolves each reference file (car tables from gt7info, `index.json`/`signatures.json` from gt7-datalogger-track-data) from `runtime/gt7/` when that copy validates, else from `src/assets/gt7/`. `signatures.json` never ships (upstream states no licence for it), so recognition of catalogue tracks starts after the first successful update; until then only learned tracks match. A relay start downloads nothing by default. Explicit `RACECAST_GT7_DATA_UPDATE=1` enables `gt7_data.update` at most once per 24 h in a daemon thread. The same thread then compares `gt7_data.fingerprint` (os.stat of every loaded file, learned file included) every 60 s and swaps a new `CarDB`/`TrackDB` into the store and, through `TelemetryStore.data_listeners`, into the Engineer analysis, so a manual `racecast gt7-data update` reaches a running relay within a minute. The lap accumulator keeps `(x, z)` every 20 m, up to 40 km per lap; after each closed lap `TrackDB.match` checks length (3 %), box, mean distance to the racing line (15 m) and driving direction, so a reverse layout is told apart from its forward twin. `/status` `telemetry.track` reports it; a session boundary clears it. A lap that matches nothing logs one `GT7 track: no match for a <length> m lap` line per session (layouts whose upstream capture was dropped, e.g. Autopolis Short Course, have no line and need a Set track). The exporter decides the track per GT7 session and measures `lap_dist_m` along the racing line. Learned signatures and recording assignments live in `runtime/gt7/learned-tracks.json`, which no update touches; a downloaded line wins over a learned row for the same layout or its reverse. Tests: `tests/test_gt7_data.py`, `tests/test_gt7_tracks.py`, `tests/test_telemetry_endpoints.py`.

**Driver telemetry invite and ingest (#1111).** `driver_invite` keeps one invite per event in `runtime/<profile>/driver-invite.json` (read per request): `event start` creates it for a fresh session and keeps it for a takeover or recovery restart (a takeover on another machine creates one, since the Funnel host changes anyway), `event stop` deletes it, `event invite --new` and the Control Center's **New link** replace it while an event runs (between events they refuse). The roster check uses `Hub.entry_for`, so a sender reassigned off a removed entry keeps uploading. A connection quiet for `FORGET_S` (10 min) is forgotten, but its reassignment stays, since the code still names the old entry; reassignment and disconnect records are each capped at four times the connection limit; the hub resets when the invite id changes. Tailnet: `GET /drivers/data`, `POST /drivers/disconnect {conn}` (410 for that code afterwards). Contract: `src/docs/design/driver-telemetry-ingest.md`; driver guide: wiki Driver-Telemetry. Tests: `tests/test_driver_invite.py`, `tests/test_driver_ingest.py`, `tests/test_driver_routes.py`.

**Driver race (#1112).** The hub's `on_sample` feeds every sample (dated by packet id within its batch) to `driver_race.Service`, which holds one `race_distance.Race` along the picked layout's `reference_trace` and rebuilds it when the pick changes. GT7's counter reads 0 on the grid; the finish line's station is learned per car from its own crossing (a car without one uses the agreeing medoid of at least `LINE_QUORUM` counting entries), a late sender starts at most on the leader's lap, a change needs a lobby counter of at most 2, the counter gives whole laps and the projection the fraction, and only within `SNAP_M` of the line may the prediction move a sample a lap. Single lobby finishes on GT7's counter including lap 1 (formation lap), checked against distance; endurance on the final lobby's counter of a car that took over after the final switch. Every sample is checked before it changes anything (finite, inside the line's area, in time order, plausible step), because it comes from a driver's machine. Box = standing more than `BOX_LATERAL_M` off the line (unconfirmed until the #1110 pit measurement). Only `relay.mode == "race"` feeds it; the race lives in memory. `stint_switch_watch` opens the driver change window when the on-air row changes and passes the last row's `Laps` cell (`ScheduleSource.final_laps`, kept out of the 4-tuple rows), else the event setting; it marks the last row on air even without a count, so a `lap_count` set later reaches the final lobby (`Service.set_settings`) without moving the final switch time. Tailnet: `GET /drivers/race`, `POST /drivers/race/{settings,final-lap,finish,reset}`; desk controls come with #1114. Race Control actions (#1113): `POST /drivers/race/{red-flag,restart-mode,release,rejoin,correct,change}` with identity `tailnet` until the desks pass theirs; a red flag freezes every entry and each resumes from its anchor (keep, or neutralise per lap) when a car of the restart lobby leaves the box. `POST /drivers/race/estimate` (`{entry, ref, seconds}` or `{entry, clear: true}`, both desks) puts a quiet car where its reference was `seconds` ago (`Race._advance` over the fine and coarse history, `_distance_at`), status `est` over `no_data`/`dc`, gaps = the reference's plus `seconds`; in memory only, frozen under a red flag (folded into the restart anchor) and after the flag, ended by the car's next data (`estimate_end` in the audit). `release` lets a car still in its old session count on (a mis-press); a single lobby counts finish laps in race distance, because a restart from the box shifts the restart lobby's line. Corrections and rejoin marks persist in `runtime/<profile>/driver-race-actions.json` until a race reset (`Service.reset`, which keeps the file's tyre compounds and qualifying corrections) or a fresh `event start` (`driver_race.clear_actions`, which empties it), every action appends to `driver-race-audit.jsonl`, and the league's restart default is `profiles/<name>/driver-race.json` (travels with `profile export`). Tests: `tests/test_race_distance.py`, `tests/test_driver_race.py`, `tests/test_driver_routes.py`.

**Race recording and disconnect events.** `src/scripts/race_recording.py` holds the `Store` (one SQLite file per event, `runtime/<profile>/race-recording-<UTC stamp>.sqlite`, named by the pointer `race-recording.json`), a bounded `Writer` thread (120 jobs; `failed` and `dropped` show in the status) and the `Recorder`. `driver_race.Service.open_recording()` opens it in race mode right after the control port is bound; before that call neither the tick nor a request opens or creates a store (a start answers 503), after it the first race-mode tick opens one that is missing (a qualifying relay creates no file, its status is an empty placeholder and a manual start answers 409) and feeds it from the tick with the live, undelayed `standings()`, in race mode only; a recording error is logged once, retried after `RECORDING_RETRY_S` and never stops the tick or the fastest-lap save; the routes answer it with 503. The Writer logs its first failed write once. One sample per second on a fixed grid (a wall clock jump back or more than 2 s ahead starts a new one), a JSON doc `{state, red_flag, rows}` (`pos` = index + 1, `compound` from the saved actions). It starts when the first car counts (`racing`, `final_lap`, `finishing`) and stops when the state turns `finished`, which re-arms the auto start for the next race; a manual stop is not undone by the auto start, and the first observe after a restart is a baseline, so a restart in a finished race keeps a manual recording. Director and Race Control start and stop it by hand. `rotate` (a fresh `event start` with the relay stopped) clears the pointer so the next use opens a new file; an `event start` on a running relay continues the current recording, like the invite. The running flag lives in the file's `meta`, so a relay restart resumes it. A disconnect is suspected while the recording runs, when a car with a distance is quiet for more than `race_distance.NO_DATA_S` (5 s), dated by its last packet; none for a car in the box during the change window, none under a red flag, none for a row still `waiting` for its red flag restart (a standings field), none for a finished car. Data that returns while the recording is stopped still ends the dropout. An event whose add job the Writer dropped stays in memory only, and its later updates are lost with it on a restart. States `suspected`, `dropout` (data came back), `confirmed`, `dismissed`; `decide` may re-decide. Decisions and start/stop go to `driver-race-audit.jsonl`. The CSV carries the sample's `state` and red flag mode on every row; `csv_rows` neutralises cells starting with `=`, `+`, `-`, `@`, tab or CR with a leading `'`. The timing tower (`src/obs/drivers.html`) shows `gap_s` (to the leader); standings rows also carry `gap_time_s`/`interval_time_s`, exact times for lapped cars, which only the desks show (`+1 L · 1:02.5`) and `driver_race.public_view` never carries. Tailnet routes: `GET/POST /drivers/race/recording` (`{action: start|stop}`), `POST /drivers/race/recording/event` (`{id, decision: confirm|dismiss}`), `GET /drivers/race/recording/at?time=<epoch s>` (the nearest sample, 404 without one), `GET /drivers/race/recording/csv`; the Director and Race Control policies allow them under `/console` and `/console/race-control`. The query parameter is `time`, never `t` (the console token). `GET /drivers/snapshot?time=` serves `src/console/race-snapshot.html` (also `/console/drivers/snapshot` and `/console/race-control/drivers/snapshot`, role-gated, relative fetches); the desk's **Show standings** opens it 5/10/15/20/30 s (default 10) before the event's last packet, **Browse recording** opens it without a time (the end of the span), and the slider spans the whole recording and refreshes it every 10 s. A trailing slash redirects to the path without it, because the fetches are relative; the page sets the console cookie only for a token the gate verified. `gap_time_s`/`interval_time_s` are None while the car ahead is quiet. The desk sound on suspicion is per browser and off by default. Tests: `tests/test_race_recording.py`.

**Public live timing (#1128): the first unauthenticated path through Funnel.** Everything else under `/console` needs a console identity, and the two other exceptions (`/console/drive`, `/console/probe/ingest`) only take telemetry in. `/console/timing?l=<id>` serves `src/console/timing.html` and `/console/timing/data?l=<id>` the delayed dashboard snapshot cut by `driver_race.public_view` (no connection ids, positions, corrections, authors, stream URLs, chat or controls; compound and fuel always, the display switches only hide them on air). The id comes from `runtime/<profile>/timing-link.json` (`timing_link`, the invite's file format), separate from the drivers' invite: `event start` creates it (fresh event) and `event stop` clears it, `racecast event timing --new` and the Control Center's Home row renew it while an event runs, and both desks show it (`GET /drivers/timing-link`). The handler compares the id in constant time, answers GET only, rate-limits wrong ids in a bucket of its own (a crowd holding an old link never turns a driver's 403 into 429), and paces the data route through an upload budget instead of a viewer cap: `timing_feed.TickBody` builds the public JSON at most once per 2 s tick, gzipped, with an ETag (`If-None-Match` gets a 304), and `timing_feed.Budget` estimates the viewers from the responses it served and sends each one the next poll interval in `X-Poll-After` (2 to 30 s) so that all of them stay within `RACECAST_TIMING_BUDGET_KBPS` (machine `.env`, default 1000 kbit/s). Nobody is turned away for load; a 300 requests per second cap remains only against abuse, and its 429 also carries `X-Poll-After` and counts as demand, so a crowd arriving at once spreads out. The estimate window is 60 s, twice the longest interval, because a shorter one misses slow pollers and the crowd oscillates (`t_an_obeying_crowd_stays_near_the_budget`). Until the samples cover the whole window (a crowd that just arrived), the estimate divides by the span they do cover, at least 2 s, and each handed-out interval is spread up to half the need around it (inside 2 to 30 s), so a crowd that arrived together does not keep returning together (`t_a_crowd_arriving_at_once_stays_near_the_budget`). Every answer counts `timing_feed.HEADER_BYTES` on top of its body. The 30 s ceiling bounds what the budget can hold: at the default 1000 kbit/s and about 950 bytes per answer that is roughly 4000 viewers, beyond which the upload grows with the crowd again. Revalidation follows RFC 9110 (`timing_feed.etag_matches`: lists, `W/`, `*`); gzip and plain bodies carry their own strong ETags, and `Accept-Encoding` is parsed with q-values (`accepts_gzip`). A failing build keeps serving the last good body (one retry per tick); without one the route answers 503 with `X-Poll-After`, and the error is logged once. `X-Data-Age` tells the page how old the tick body is; the payload's `remaining_running` (the race timer's mode) and `delay_s` let it count down locally and name the delay. The page is built once per relay process and served gzipped with an ETag. `/console/timing/brand/<key>?l=<id>` serves brand logos behind the same id check and failure bucket, with an abuse cap of its own (`TIMING_BRAND_RPS`) and outside the poll budget, but held to its rate by `brand_logos.ByteWindow` (`RACECAST_TIMING_BUDGET_KBPS` over 10 s, at least one logo; beyond it 429 with `Retry-After`): only a key in the Configuration roster, only `brand_logos.Logos` (the league override `runtime/<profile>/brands/<key>.png`, then `src/assets/brands/<key>.png`, PNG magic, at most `MAX_BYTES`), `Cache-Control: public, max-age=86400`, `nosniff`. On Funnel the page builds the logo URL beside its own path (`TimingLogic.brandUrl`, only `l=` carried) and retries a failed logo after a minute, doubling per failure up to 30 minutes. The public body names a brand only while its logo resolves (`driver_race.public_brands` in `_timing_public`), so no viewer polls a missing one. The budget, the tick and the interval touch only these two routes: `driver_race`, `/drivers/dashboard` (the stream overlay) and every other `/drivers/*` route (Race Control, the desks) are never paced (`t_internal_dashboard_routes_ignore_the_timing_budget`).

**Timing host (#1161).** A league with `TIMING_HOST_URL` and `TIMING_HOST_PUBLISH_KEY` in its `profile.env` gets an external fan-out: `timing_publish.Publisher` (a relay thread from `_start_timing_publisher`, idle without a host) holds one TLS WebSocket (`ws_client`, `obs_ws` framing) to `wss://<host>/t/<link id>/publish?v=1` and sends the tick body as a `state` frame every 2 s (`timing_host`: frame builders, `read_settings`). The Cloudflare Worker (`src/timing-host/worker.js`) fans it out per link id in a Durable Object and acks; 15 s without an ack reconnects, failures back off to 30 s and warn once. The publisher re-reads the host keys from `RACECAST_PROFILE_ENV_FILE` when `POST /drivers/timing-host/reload` (tailnet only, never under `/console`) nudges it, so a deploy or settings change needs no restart; a changed or cleared timing link sends `end` to the old room, over one bounded connection of its own when the publisher is disconnected. `event stop` and `event timing --new` nudge the publisher, and `event stop` waits up to `TIMING_END_WAIT_S` while `status()['room']` says it still owes the old room its `end` before it stops the relay. Both pages run side by side: the served path (`timing_link.served`, `runtime/<profile>/timing-served.json`, `hosted` by default with a host, reset by a fresh `event start`, kept by a renewal) decides which link the desks, `racecast event timing` and the Control Center Home row offer. While `hosted` is served and the publisher is connected, the Funnel data carries `moved_to` (the hosted link), except while the publisher's quota estimate (`requests_today` + messages / 20) is at or above `QUOTA_GUARD_REQUESTS` (90 % of 100,000): then `status()['quota_low']` is true (shown in the Home row and the desks), the publisher sends `moved` toward Funnel, and only a new UTC day lifts it, because the estimate adds the rooms the publisher left that day (`_requests_base`); switching to `funnel` (`event timing --serve funnel`, Home row switch) sends `moved` to the room. The page's transport decisions are the pure `TimingLogic` block in `timing.html` (deno tests in `tests/timing-host/page_test.js`): a hosted page falls back to Funnel (`from=host`) after 3 failed reconnects and 12 s since the drop, a deliberate move arrives as `from=moved`, and the Funnel page follows `moved_to` back after a dwell (10 s moved, 60 s fallback). `GET /drivers/timing-link` adds `served`, `hosted_url`, `funnel_url` and the publisher's `status()`. The Funnel URL (also each state's `fallback`) exists only while Funnel serves `/console`: `_funnel_watch` answers from a cache and asks the tailscale CLI in the background at most once a minute, never in a request. Its `magicdns()` also feeds the control server's Host check (`_browser_request_allowed`), so a MagicDNS name that appears after the relay started is accepted without a restart (the relay's watch also refreshes itself every 30 s, so the name is known within about a minute of Tailscale coming up, before anyone asks); `POST /console/drive/ingest` and `/console/probe/ingest` skip the Host check, since they authenticate by a custom header a cross-site page cannot set. Brand logos travel as `brand` frames (`timing_host.brand_frame`, base64 PNG) after the first state, one per step, each once per connection and again when its bytes change (`brands_fn`, the Funnel route's resolver); they count in `msgs_today`, and a failed logo send pauses logos for `BRAND_PAUSE_S` so a slow uplink keeps its states. The room keeps at most 64 as base64 under `brand:<key>` (PNG magic, 256 KiB, `[a-z0-9-]{1,64}`) and delivers them over the viewer sockets, never as requests (Cloudflare bills only incoming socket messages): each logo to a new viewer after the state, and a new or replaced one to every connected viewer; `end` deletes them with the room. The Worker has no logo route. The hosted page (`TimingLogic.brandMessage`) turns each into a blob URL (the room's CSP allows `blob:` images) and never requests a logo. The publisher only reads the delayed body; it never touches `driver_race` or the feeds (`t_internal_dashboard_routes_ignore_a_dead_host`).

**Driver telemetry desks (#1114).** `src/console/driver-desk.js` (public static code at `/driver-desk.js` and `/console/driver-desk.js`, served before the gate like `driver-radio-ui.js`) renders the same controls in the Race Control desk (`base` `/race-control`) and the Director Panel (`base` ""). Routes beyond #1112/#1113: `GET /drivers/readiness` (`driver_ingest.readiness`, with `focus` = the stint on air and the next), `GET /drivers/invite` (the id, and `base`, the Funnel address while Funnel serves `/console`; the desks build the link from it, else from their own origin, and prefer the timing link's `funnel_url` the same way), `POST /drivers/reassign {conn, entry}` (`Hub.reassign` keeps the sender's slot under the new entry; the race moves the car and parks an old entry with no car left, keeping its distance, corrections and the car's counting state, so moving the car back resumes the team). **First program change for Race Control over the Funnel:** `POST /console/race-control/red-flag {on}` raises (or lowers) the Standby Cover in `obs_ws.graphic_scene`, sets the HUD banner `RED_FLAG_BANNER` through `SetupControl.set_field` (needs the webhook and the Configuration vocabulary, exactly like the panel's RED FLAG) and holds the race; it reports `cover`/`banner` so the desk can say what failed (never the OBS note, which can name the WebSocket host), and logs a WARNING with the identity. `{on:false}` lowers the cover and clears the banner only when this route turned the cover on (`relay.rc_red_flag_raised`: set only when the cover was down before the raise, kept by a later raise over it, cleared by any director, Companion or auto-cover switch of it), never an auto-cover over a dead feed (#495) or the director's own; one change per person in `RED_FLAG_MIN_S`. The panel's own RED FLAG also posts `/drivers/race/red-flag` when it raises the cover. Last change wins; `last_action` shows its author in both desks. Tests: `tests/test_console.py`, `tests/test_driver_routes.py`, `tests/test_driver_ingest.py`.

**Driver telemetry probe (#1110).** Maintainer measurement before the driver dashboard, off unless `RACECAST_TELEMETRY_PROBE=1` at relay start. `telemetry_probe.Probe` holds a random key per relay start; `POST /console/probe/ingest?sender=NAME` with `X-Probe-Key` is handled in `_console_gate` before the token check (failed keys share the console auth-failure rate limit). The body is batch format v1 (`RCT1`, then uint16 length plus the packet as the console sent it, at most 120 packets). The probe decrypts the first 128 bytes of every packet for the magic and the packet id (loss counting through `gt7_packet_stats`) and every 6th packet whole as a sample; 15 senders at 60 Hz cost about a third of one core in pure Python. Nothing is written to disk. Per-sender `packets` are totals over every stream (an upload stall over 5 s or a replay loop starts a new `gt7_packet_stats` stream; `current_stream` shows the open one). Senders are told apart by name only, so every sender needs its own name. A probe during a live event shares the relay's CPU with the feeds: after a Funnel outage 15 senders catch up with up to 600 packets each. `GET /telemetry/probe` (tailnet) returns the key and per-sender counters and samples, `POST /telemetry/probe/reset` clears them. The sender is `src/relay/racecast-sender.py` (stdlib only, format `A` heartbeat, `--forward` and `--listen` modes). It binds one interface, never all: the one that reaches `--console` (or the default route while discovering), loopback with `--listen`; `--bind` overrides. It removes posted packets by sequence, drops a batch the relay refuses (400), retries a refused key once a minute, survives Windows' UDP `WSAECONNRESET`, and searches a discovered console again after 30 s of silence; `tools/gt7-sim-ps5.py` and `tools/gt7-probe-load.py` are the test tools. Tests: `tests/test_telemetry_probe.py`, `tests/test_telemetry_sender.py`.

**Picked track layout (#1129).** `gt7_track_pick` keeps the event's GT7 layout in `runtime/<profile>/event-track.json` for every profile kind; it stays until changed. The relay builds one `Controller` at start: it hands the pick to `TelemetryStore.set_track_pick` (which also forwards it to the Engineer analysis) and writes it into `<stem>.track.json` beside the open recording, on recording open and on every change. It never touches `learned-tracks.json`, whose stat is part of `gt7_data.data_version` and would invalidate every lap index. `session_tracks(..., pick=)` names a session after the pick unless its longest matching lap names another layout that does not list the pick among its `alternatives`; a Set track still wins. A replay (`reset_analysis` with `active`) runs without the pick in the HUD and the Engineer. `TelemetryEngine` keeps the pick separate from recognition: `track` is the pick from the first packet and after a session change, `track_check` is what recognition named this session, and `track_mismatch()` is true when that lap names another layout and the pick is not among its `alternatives`. The mismatch is a quiet health yellow (`track_mismatch`, excluded from the notify level). Routes: `GET|POST /event/track` (Director, `["event","track"]` director-tier over the Funnel) and `GET|POST /console/race-control/track` (race_control); `/status` and `/console/race-control/data` carry `track_pick`. `?layouts=1` adds the layout list; polls leave it out. CLI `racecast event track` and Control Center `/api/event-track` talk to the relay only when it runs the active profile. Recording deletion removes the sidecar. Before a lap of the session completes, the Engineer desk draws the outline from `GET /console/race-engineer/outline?track=` (`TrackDB.reference_trace`, downloaded lines only). Tests: `tests/test_gt7_track_pick.py`, `tests/test_track_pick_routes.py`.

**Audience widgets (#932).** The relay owns one `audience_widgets.Runtime` and

**Audience providers (#933, #934).** Relay-owned YouTube and Twitch workers start
only after successful mandatory control-port binding. `/audience/admin/youtube`
and `/audience/admin/twitch` are exact producer-loopback routes before Console
routing, with socket/Host/Origin/Referer/Fetch Metadata checks and bounded JSON.

OBS, switch inputs, clear manual goals or require anonymous chat authorization.
