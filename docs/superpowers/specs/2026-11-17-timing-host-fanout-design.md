# Public live timing: external fan-out through a Cloudflare Worker

Issue: #1161. Follows #1128 (the page) and #1160 (the upload budget). Epic #1109.

## Intent

Since #1160 the public live timing page is served from the producer's machine through Funnel and
paced by `RACECAST_TIMING_BUDGET_KBPS`. Beyond about 4000 viewers the page sits at its 30 s ceiling
and the upload grows with the crowd again. Viewer numbers cannot be estimated per event, so a league
can hand the fan-out to an external host: the relay sends one state per tick, the host distributes
it to every viewer. Without a configured host everything stays as today.

## Goals

- An optional per-league timing host. Configured: viewers get a hosted link; the relay uploads one
  state per tick regardless of the viewer count.
- racecast defines a small publish protocol; a Cloudflare Worker with one SQLite-backed Durable
  Object per event is the shipped, tested implementation.
- racecast deploys the Worker itself through the Cloudflare REST API (issue option A). No Wrangler,
  no Node on any producer machine.
- When the host fails mid-event, connected viewers fall back to the Funnel page on their own.
- The producer sees whether the host is live and how many viewers it holds.

## Hard boundary (unchanged from #1160)

`driver_race`, `/drivers/dashboard` (stream overlay) and every other `/drivers/*` route (Race
Control, the desks) are never paced, delayed or routed through the host. The publisher only reads
the newest delayed public body; it never triggers or slows anything upstream and never touches the
feeds. A failed or slow host never blocks a relay thread that serves anything else.

## Non-goals

- Other providers. The protocol is documented so one could be added; only Cloudflare ships.
- Custom domains, R2, paid-plan features. The Worker runs on `*.workers.dev` on Workers Free.
- Changing the Funnel path or its budget. It stays as the fallback and the no-host default.
- Creating the account's workers.dev subdomain. The league sets it once in the Cloudflare dashboard
  (Workers & Pages, Account details, Subdomain); racecast reads it and reports a clear error when it
  is missing. The REST endpoint for creating it could not be verified.

## Approaches considered

- **Persistent WebSocket from the relay to the Durable Object (picked).** Incoming WebSocket
  messages are billed 20:1, so a 24 h event at a 2 s tick costs about 2,200 of the 100,000 daily
  requests instead of 43,200 and leaves room for about 48,000 viewers (page load plus socket each).
  Costs a publisher thread
  with TLS, reconnect and an application-level ack, since a WebSocket has no per-message status.
  Endurance leagues run 24 h events, so the quota gain decides it.
- **One HTTPS POST per tick.** Stateless, measured in the spike, a status per publish. Rejected for
  the quota cost on long events.
- **POST with a 4 s tick.** Halves the cost, still 21,600 per 24 h. Rejected for the same reason.
- **Deploy via Wrangler (B) or a wiki guide (C).** B needs Node on every producer machine including
  Windows; C puts the deployment on each league. The REST API supports what A needs (see below).
- **Fallback by polling the Funnel data from the hosted page** instead of redirecting. Needs CORS on
  the relay's timing route. Rejected for a top-level redirect.

## Decided

### League configuration (`profiles/<name>/profile.env`)

- `TIMING_HOST_ACCOUNT_ID` and `TIMING_HOST_API_TOKEN` (permission: Workers Scripts Edit) are set
  by the league. Both empty means no host and today's behaviour.
- `TIMING_HOST_PUBLISH_KEY` is generated by racecast on the first deploy (like `CONSOLE_SECRET`) and
  installed as a Worker secret. The relay authenticates its publisher with it.
- `TIMING_HOST_URL` (the `https://<script>.<subdomain>.workers.dev` origin) is written by the deploy.
- All four are league values, carried by `profile export` and never committed. Only the URL is
  injected (`RACECAST_TIMING_HOST_URL`); the token and the key stay in profile.env, so no child
  process inherits them. The relay reads the URL and key from the file (`RACECAST_PROFILE_ENV_FILE`). `profile show` masks the token and the key.
- The Control Center's league settings get fields for account id and token (the other two are
  shown read-only).

### Deploy (`racecast` verb plus its Control Center action)

- A new CLI action deploys or updates the Worker for the active league and a status action reports
  it. The Control Center gets the same two actions next to the timing host settings.
- Deploy steps, all over REST with the league's token:
  1. Read the account's workers.dev subdomain. Missing: fail with the dashboard instruction.
  2. `PUT /accounts/{id}/workers/scripts/{script}` multipart: `metadata` with `main_module`,
     a fixed `compatibility_date`, a `durable_object_namespace` binding to the room class, a
     `secret_text` binding with the publish key, and `migrations` with `new_sqlite_classes` for the
     room class on the first deploy (later deploys carry the matching tag, since an account with a
     migration tag requires one on every upload). The Worker module and the viewer page are separate
     parts; the page is uploaded as a text module the Worker imports.
  3. `POST /accounts/{id}/workers/scripts/{script}/subdomain` with `{"enabled": true}`.
  4. Store `TIMING_HOST_URL` and, on first deploy, `TIMING_HOST_PUBLISH_KEY` in `profile.env`.
- Verified against a Workers Free account (2026-11-17, Task 1 of the plan):
  - `GET /accounts/{id}/workers/subdomain` returns `result.subdomain`.
  - The first upload carries `migrations: {"new_tag": "v1", "new_sqlite_classes": ["TimingRoom"]}`
    and returns `result.migration_tag: "v1"`. Later uploads succeed both without `migrations` and
    with `{"old_tag": "v1", "new_tag": "v1"}`; the deploy sends none once the tag is `v1`.
  - The current tag is readable from `GET /accounts/{id}/workers/scripts` (`migration_tag` per
    script), not from `.../scripts/{name}/settings` (it answers `null` there).
  - Modules are multipart parts with `application/javascript+module`: `index.js` (main module,
    calls `setPage`), `worker.js`, `page.js` (the viewer page as `export default "<html>"`).
  - `POST .../scripts/{name}/subdomain {"enabled": true, "previews_enabled": false}` serves it at
    `https://<script>.<subdomain>.workers.dev`; it answered within a few seconds.
  - Token permissions used: Account, Workers Scripts: Edit and Account Settings: Read.
  - End to end with the relay's `Publisher` and a `WsClient` viewer: state, ack with viewers and
    `requests_today`, `end` forwarded, page 410 afterwards.
- One script per league: the script name is derived from the profile name, so two leagues on one
  Cloudflare account do not collide.
- The deploy stamps a content hash of the Worker and page into the Worker. Status compares it with
  the shipped files and reports "update needed" after a racecast update.
- Deploy and status go through `http_util` (repo rule).

### Publish protocol (relay to host)

- Endpoint: `wss://<host>/t/<link-id>/publish` with `Authorization: Bearer <publish key>`. The
  Worker rejects a wrong key with 401 before touching a Durable Object. The link id is the event's
  timing link id and names the Durable Object, so each event and each renewed link gets its own room.
- Relay to host, text frames of JSON:
  - `{"t": "state", "seq": n, "age_s": a, "data": <public_view body>, "fallback": "<funnel url or
    null>"}` once per tick (2 s), the same bytes `timing_feed.TickBody` already builds; `age_s` is
    the body's age at send time (today's `X-Data-Age`). The room stamps its receive time, so a
    viewer always gets the true age.
  - `{"t": "end"}` on `event stop` and on link renewal (to the old link's room).
- Host to relay: `{"t": "ack", "seq": n, "viewers": k}` at least every 5 states. No ack for 15 s
  counts as a dead connection: the publisher closes and reconnects.
- Relay to host: `{"t": "moved", "to": "<funnel url>"}` when the producer switches the served path
  to Funnel (see "Choosing and switching the path"), `{"t": "moved", "to": null}` when it switches
  back and on every fresh publisher connection while hosted. The room keeps the last `moved` target
  and sends it to viewers who connect later.
- Host to viewers, besides `state` and `end`: `{"t": "publisher", "up": bool}` when the publisher
  socket closes or returns, and `{"t": "moved", "to": url}` forwarded from the relay.
- The ack also carries `requests_today`: viewer page loads plus socket upgrades this room served
  since 00:00 UTC (each viewer costs two Worker requests). The room stores it with the state.
- Room states: unknown (no publish yet), live, ended.
  - Unknown: the page and the socket answer 404 "unknown timing link". A room only becomes live
    with its first publish.
  - Live: the room keeps the last state in memory and persists it at most every 30 s (so a room
    evicted and woken can answer a new viewer; this keeps SQLite writes at about 2,900 per 24 h).
  - Ended: on `end` the room forwards `end`, closes every viewer socket, deletes the state and keeps
    a small tombstone so the link answers "this timing link has ended". An alarm purges the
    tombstone after 7 days.
- Orphaned room: when no publisher was connected for 30 minutes (relay stopped before `event stop`,
  or crashed), an alarm ends the room as if it got `end`. `event stop` itself sends no `end` when
  the relay is not running.
- Versioned with `"v": 1` in the publish URL query or first frame (builder's choice); the Worker
  rejects unknown versions so an old relay never feeds a newer page silently.

### Viewer side (host)

- `GET /t/<link-id>` serves the viewer page; `GET /t/<link-id>/ws` upgrades to a viewer socket
  through the Hibernation API (`ctx.acceptWebSocket`). The link id format is checked in the Worker
  before a Durable Object is addressed; a malformed id is a 404 without a Durable Object call.
- Viewers send nothing after connecting (inbound messages would count against the quota).

### Viewer page (one source, two transports)

- `src/console/timing.html` stays the single page. Served by the relay it polls as today. Served by
  the Worker it opens the WebSocket, renders each `state`, and keeps the local countdown and the
  data-age display it has now.
- Fallback (user decision (b)) is for a failing host, not a missing publisher. The page redirects
  with `location.replace(fallback)` when 3 attempts after the drop of its socket failed and at
  least 12 s passed since the drop; the drop itself is not a failed attempt, and a state on a new
  socket resets the count. Silence on an open socket never redirects: when the relay machine loses
  power or network, the room learns it late (no close frame), and Funnel runs on that machine too.
  A `publisher: false` message, or 20 s without a state, shows "relay reconnecting" with the
  stale-data age. The relay sends a `fallback` only while Funnel serves `/console` (checked at most
  once a minute in the background); without one the page keeps retrying with backoff from 1 s to
  8 s. After 6 failed attempts it says "timing link unavailable" and retries every 2 minutes; 30
  minutes after the drop it stops (a refused socket, 404 or 410, is a billed Worker request).
  Fallback URLs must be https.
- The redirect names its reason: `from=host` for the automatic fallback, `from=moved` for the
  producer's switch to Funnel. The Funnel page follows `moved_to` at once for a plain visit, after
  10 s for `from=moved` (the room may still hold the old move for a moment) and after 60 s for
  `from=host`, so a flaky host cannot bounce viewers back and forth. `moved_to` appears only while
  the host is served and its publisher is connected.
- Known limit: when the daily request quota is exhausted, Cloudflare does not serve the page at all
  (error 1027). The redirect then reaches only viewers already connected.
  The publisher's socket can stay up meanwhile, so `moved_to` still sends returning Funnel viewers
  to the host after their dwell; the producer switches to Funnel before the quota runs out.

### Relay publisher

- A daemon thread in the relay that publishes while host settings exist and a timing link exists.
- Host settings change without a relay restart: deploy, the settings save and the path switch tell
  the running relay over the control port to re-read the `TIMING_HOST_*` keys from the league's
  `profile.env` (the relay's standalone `load_dotenv` copy; `racecast` passes the profile.env path
  at relay start). A host set up mid-event is used at once. It reads the current link through `timing_link.Cache` each tick, so
  `event stop` and `event timing --new` take effect without a relay restart (send `end` to the old
  room, connect to the new one).
- WebSocket client from the stdlib: reuse `obs_ws` framing (`encode_frame`, `decode_frame`,
  handshake helpers, client masking), wrapped in `ssl` with certificate verification. Every socket
  operation has a timeout. Reconnect with capped exponential backoff.
- Its status (`connected`, `last_ack_age_s`, `viewers`, `last_error`) is exposed on
  `/drivers/timing-link` and to the Control Center.

### Choosing and switching the path

- With a host configured, both paths run side by side for the whole event: the Funnel page works as
  today and the relay publishes to the host. A distributed link cannot be recalled, so switching
  means moving the viewers who are on the other page.
- The producer picks the served path, `hosted` or `funnel`: a CLI option on `racecast event timing`
  (name left to the builder) and a switch in the Control Center Home row. It is stored with the
  event's timing link (`runtime/<profile>/`), so it survives a relay restart and ends with the event.
  Default with a host configured: `hosted`. Without a host only `funnel` exists.
- The served path is the link the desks (`/drivers/timing-link`), `racecast event timing` and the
  Control Center Home row show on top as the one to hand out; the other one is shown below as the
  fallback. A host that is down shows as a warning there; nothing else reacts to it.
- Switch to `hosted`: the Funnel data carries `moved_to` with the hosted link, and Funnel pages
  `location.replace` to it on their next poll. Switch to `funnel`: the relay sends `moved` to the
  room and hosted pages redirect at once. The automatic fallback on a failing host stays in addition.
- The Control Center and the desks show the host's viewer count and an estimate of today's request
  use (`requests_today` plus the publisher's message count / 20), so the producer can switch to Funnel
  before the quota runs out. The estimate does not count other Workers on the same account; the docs
  say so.

### Tests and CI

- Python: publisher (framing, ack timeout, reconnect, link switch, end marker), deploy request
  shapes against a fake API, config and masking, the `/drivers/timing-link` payload, and the
  boundary test from #1160 extended: with the host down or slow, `/drivers/dashboard` still returns
  every snapshot immediately.
- Worker: unit tests run with `deno test` against stubbed Durable Object state and WebSocket objects
  (deno is already a runtime dependency). CI gets a deno setup step and runs them.
- No test talks to Cloudflare. The real account is checked by hand once before merge (deploy, a
  publish, a viewer, the fallback redirect, the end marker).

### Shipping and docs

- The Worker source lives under `src/` and is included in `dist/` and in the binary's data files.
- `src/relay/CLAUDE.md` and the wiki (`Driver-Telemetry.md` plus a setup section: Cloudflare
  account, subdomain, token permissions, the deploy action, the quota numbers) describe it.
- Every changed Control Center view and desk gets its wiki screenshot refreshed in the same change.
- The docs recommend one Cloudflare account per league: the request quota is per account, so two
  leagues on one account running events the same day share it. Two leagues on one account work
  (one script each) but are not budgeted for.
